虚拟内存 / 18

malloc(100) 真的向内核要了 100 字节吗？

通常不会。malloc 面对的是进程已有的虚拟地址空间和分配器维护的块；是否需要请求新的映射、何时获得真实物理页、何时把内存归还给内核，都取决于内存分配器和操作系统。理解这层区别，才能真正解释碎片、驻留集和分配失败。

实例以 Linux/POSIX mmap 与 C11 分配接口为主；分配器组织策略使用教学模型，不把某个 glibc 版本的阈值、时间复杂度或碎片率当成跨平台定律。

18.1 映射虚拟区域，不等于立即分配全部物理页

mmap 在进程的虚拟地址空间创建映射，并指定权限、共享方式与后备对象。对于常见的私有匿名映射，读写页可能在首次访问时才逐步关联物理内存；有些读操作能共享只读零页，而写入通常需要可写的实际页面。具体何时兑现内存受内核、预取、页面大小和内存压力影响。

#define _GNU_SOURCE  /* Linux: MAP_ANONYMOUS */
#include <sys/mman.h>
#include <stdio.h>
#include <unistd.h>

int main(void) {
    long ps = sysconf(_SC_PAGESIZE);
    if (ps <= 0) return 1;
    size_t len = (size_t)ps * 2;
    void *p = mmap(NULL, len, PROT_READ | PROT_WRITE,
                   MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (p == MAP_FAILED) { perror("mmap"); return 1; }
    ((volatile char *)p)[0] = 7; /* 触碰第一页 */
    if (munmap(p, len) == -1) { perror("munmap"); return 1; }
    puts("mapping-released=1");
}

文件映射还要区分 MAP_SHARED 与 MAP_PRIVATE：前者的修改对同一映射对象的其他共享映射可见，后者的修改属于写时复制，不会直接回写原始文件。持久化与写回时机不能简单等同于“写内存立刻写磁盘”；msync() 可用于受支持的同步场景。参阅 mmap(2)。

18.2 malloc 与内核之间还有一个分配器

malloc(100) 请求的是至少可用 100 字节的对象存储，不是要求内核为该调用新建 100 字节物理页。分配器可从已有空闲块切出一段，维护元数据与对齐，也可能向系统请求更多虚拟区域。free 把块交还给分配器，不保证立即降低进程 RSS，更不保证立即调用 munmap。

组织方式（教学分类）搜索对象主要权衡
隐式空闲链表顺着块头遍历所有块简单但搜索可能较慢
显式空闲链表只遍历空闲块额外维护前后指针与合并逻辑
分离空闲链表按大小类选择链表或桶有利于减少搜索，但不能保证所有请求 O(1)

对同一组织方式，放置策略还可选 first fit、next fit、best fit 等。Best fit 不保证碎片一定最少；较好的局部利用率可能换来搜索成本和小剩余块。现实实现还会使用线程缓存、arena、大小类等机制。glibc 的 mmap 分配阈值可动态调整，不能机械地写成“每次超过 128 KiB 就必定调用 mmap”。

18.3 总空闲空间够了，为什么还放不下一块？

内部碎片是已分配块内因对齐、块尺寸或管理开销而未用于负载的部分；外部碎片是空闲空间被切成相互分离的小块，使大请求无法放进单个连续空闲块。注意：这是一个固定池的教学例子，不能据此断定现实中的 malloc 必然失败——真实分配器可能扩展堆或申请新的映射。

只考虑相互隔离的三个空闲块，不允许扩展池，也未计块头或对齐；真实分配器行为更复杂。

相邻空闲块可以合并（coalescing），减少外部碎片；为了定位相邻块，教学分配器常用块头/块尾记录大小和占用状态。但生产分配器的元数据安排可能完全不同。请求大小、释放顺序、对齐和生命周期通常比“一味补齐结构体大小”更值得测量。

18.4 回收：手动释放、引用计数、追踪式 GC 解决的问题不同

显式分配器需要调用者决定对象何时结束生命周期。追踪式 Mark–Sweep GC 则从栈、全局引用等根集合出发标记可达对象，再回收不可达对象；它可回收不可达引用环，但“可达”不等于“业务上仍需要”，仍然可能出现逻辑内存泄漏。

引用计数在计数归零时释放对象，却通常无法单独回收互相引用的不可达环。保守式 GC 在缺少精确类型信息时可能把看起来像指针的整数当作引用，导致对象被暂时保留。不同语言运行时和库有各自的最终化与安全约束；GC 也不是“自动修复所有资源管理问题”。

分清四个“释放”

对象不再被使用、分配器认为块空闲、虚拟映射被撤销、物理页最终可回收，是不同层次的事件，不保证同时发生。

18.5 可复现安全实验：先检查长度，再分配

即使懂得分配器的内部组织，也必须先写对调用者的长度计算。避免 count * size 在 size_t 中回绕导致意外分配过小：

#include <stdint.h>
#include <stdlib.h>

int *allocate_ints(size_t count) {
    if (count > SIZE_MAX / sizeof(int)) return NULL;
    /* count == 0 的业务语义由调用者决定 */
    return malloc(count * sizeof(int));
}

对于某些实现，申请成功与未来触页成功也不是同一件事；内核的内存提交和 OOM 行为需要另行考虑。完整示例见 examples/olah-ch18-allocator.c，其中还包含 mmap / munmap 的错误检查。可用 AddressSanitizer 做越界与生命周期检测，但它不能“证明”程序没有所有内存错误。

自测

free(p) 返回后，操作系统必然减少该进程的物理内存占用吗？

查看答案

不必然。分配器可能把空间保留在 arena 或空闲链表中，供后续复用；是否减少 RSS 或调用 munmap 取决于分配器、映射类型与实际触页情况。

归纳：分配地址、分配块和占用物理页是三件事

虚拟内存负责映射与权限，分配器负责块组织与复用，实际物理页由内核在适当时机管理。下章讨论系统级 I/O 时，文件映射与内核页缓存的联系会再次出现。
