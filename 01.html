Chapter 01 · A tour of computer systems

一行 Hello，
为什么要惊动整台计算机？

从源代码中的几个字符，到终端里的一行输出：我们借这条最短的路径，拆开编译器、处理器、存储器与操作系统之间的协作。

下面这段程序几乎没有算法。可是，如果没有编译器、链接器、加载机制、CPU、内存、系统调用和终端，它连一个字符都无法输出。

#include <stdio.h>

int main(void) {
    printf("Hello, world!\n");
    return 0;
}

理解系统，不是记住所有硬件名词，而是追问：这一次数据究竟经过了哪一层、为什么必须经过它？

字符与字节四段翻译如何执行存储层次操作系统性能上限动手验证
01 / REPRESENTATION

屏幕上的字符，存储器里只有位

源码在磁盘上是一串字节。以 ASCII 兼容编码为例，字符 H 的数值是十进制 72，对应二进制 01001000。处理器并不知道这是“问候”，它只解释约定格式下的位模式。

这解释了为什么“信息的表示”会成为下一章的主题：整数、浮点数、文本和指令，最终都要落到有限位宽的编码规则上。位本身没有意义，解释位的规则才赋予它意义。

02 / TRANSLATION

一条 gcc 命令，其实有四站

命令 gcc -o hello hello.c 看起来一步到位。实际上 GCC 驱动会协调多个工具：预处理、编译、汇编、链接。它们的输入输出不同，出错方式也不同。GCC 官方手册解释了如何在各阶段停止。

① 预处理 · hello.c → hello.i

展开头文件引用与宏、处理条件编译；结果仍是 C 语言文本。运行 gcc -E hello.c -o hello.i 即可查看。

不要把“编译器”笼统等同于“生成机器码”的单一步骤。hello.o 已包含机器指令，却通常仍有待链接器处理的符号引用和重定位信息；运行时也可能需要动态链接器和共享库协助。

抓住一个分界：构建时把源代码转成可装载的可执行文件；运行时由操作系统与运行时组件把它变成正在执行的进程。两件事不是同一阶段。

03 / EXECUTION

敲下 ./hello 后，究竟谁开始工作？

在典型的 Linux ELF 环境里，shell 创建子进程并调用 execve 来执行文件。内核建立新的进程映像，必要时安排动态链接器加载共享库。入口不是直接跳到 C 语言的 main：启动代码先完成运行时初始化，再调用 main。具体细节依赖平台、链接方式与 C 运行时。

这时 CPU 从内存中取指令、译码、执行，并用寄存器保存工作数据与控制状态；但它执行的既有应用代码，也有库代码，以及系统调用触发的内核代码。“CPU 正在跑我的程序”只是这段协作的缩写。

04 / LOCALITY

为什么 CPU 很快，程序仍然会等？

CPU 运算和数据到达 CPU 是两件事。寄存器、缓存、主存和持久存储提供了不同的容量、延迟与成本折中。程序反复访问附近的数据时，缓存与局部性通常能避免更慢的访问。

这里不列未经机器与工作负载限定的“纳秒数”或价格：缓存命中、随机与顺序访问、队列深度、设备型号都会改变实测结果。

想象遍历数组。按连续地址读取，往往可以让已取入缓存行的数据被接着使用；频繁随机跳转则更容易错过这份局部性。真实性能仍需测量，缓存不是“所有程序天然更快”的魔法。

工程边界：不要把一次 malloc 理解为立即申请了同样多的物理内存，也不要把一次文件读取等同于必定发生磁盘 I/O；操作系统页缓存和按需分配会影响实际路径。

05 / ABSTRACTION

操作系统用三种抽象，藏起复杂性

用户程序不需要直接给磁盘发设备命令，也不需要手工决定下一条指令在哪颗 CPU 上执行。操作系统通过一组互相配合的抽象，提供可编程的接口。

进程

为运行中的程序提供执行上下文和资源视图。调度使多个进程共享处理器；多核还可能真正并行。

虚拟内存

每个进程使用自己的虚拟地址空间；页表与硬件翻译将部分虚拟页映射到物理内存或触发异常。

文件 / 描述符

磁盘文件、管道、终端和套接字可通过一组相关的 I/O 接口访问，但各类对象的语义并不完全相同。

这三者也分别解释了常见的问题：程序为何能与别的进程隔离？同一个指针地址在不同进程中为何不指向同一处物理位置？为什么 printf 最后能写到终端？它们不是三个孤立的术语，而是同一次执行过程的不同观察角度。

06 / PERFORMANCE

优化一部分，为什么整体并没有那么快？

假设一次任务原本耗时为 1，其中比例为 α 的部分可加速 k 倍，其余部分保持不变、且忽略额外开销。那么新时间等于未优化部分加上被加速部分的新时间。

S=1(1−α)+αk
式 1 · 固定工作量下的 Amdahl 定律

例如 α = 0.60、k = 10，得到 S ≈ 2.17，并不是 10 倍。即使可优化部分的速度趋于无限大，加速比上限仍是 1 / (1 − 0.60) = 2.5。

亲自改动两个条件

下面是无额外开销的数学模型，不是任何 CPU 上的性能承诺。

整体加速比

原本 100 秒的任务，新耗时 46.0 秒

理论极限：2.50 倍

2.17×

这就是性能分析里“先找大头”的数学原因：若某个函数只占总耗时的 1%，即使把它优化到不需要时间，整体速度也最多提高约 1.01 倍。讨论并行化时，线程创建、同步与内存带宽等实际开销还会让结果偏离理想模型。

07 / REPRODUCE

用七条命令，把这次漫游复现出来

以下命令适用于具备 GCC、binutils 的 Linux 环境。先把本文开头的代码保存为 hello.c，再依次运行：

gcc -E hello.c -o hello.i       # 预处理结果：文本
gcc -S hello.c -o hello.s       # 编译生成汇编
gcc -c hello.c -o hello.o       # 生成可重定位目标文件
gcc -o hello hello.o           # 链接
file hello                       # 查看文件格式
readelf -h hello                 # 查看 ELF 文件头
./hello                          # 运行

想更深入，还可以运行 objdump -d hello.o 阅读目标文件的反汇编，或在装有 strace 的 Linux 上运行 strace -e write ./hello 观察输出相关的系统调用。不同工具链、优化选项和运行时会产生不同结果；实验输出不应被当作跨平台固定值。

观察 1 · 表示用 xxd hello.c 查看源码字节，找出字符 H 对应的字节值；这个命令需要本地安装 xxd。
观察 2 · 翻译比较 hello.s 和 hello.o：为什么一个可读、另一个不能直接用文本编辑器理解？
观察 3 · 抽象比较 ./hello 的输出与 strace 记录：哪个是用户可见结果，哪个展示了程序与内核的交互？

本章的收获：把“写代码 → 得到输出”分解成表示、翻译、执行、存储、抽象、测量六个可验证的问题。后续章节会逐层拆开这里暂时黑箱化的机制。
